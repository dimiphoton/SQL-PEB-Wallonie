# Décisions

| Date | Décision | Alternative envisagée | Raison |
|---|---|---|---|
| 2026-08-25 | DuckDB comme moteur SQL | SQLite ; PostgreSQL | DuckDB est un moteur analytique natif (fenêtrage et CTE de premier ordre, pas des extensions tardives). Zéro serveur, reproductible en une commande. PostgreSQL est déjà représenté dans d'autres projets du portfolio (PostGIS) ; DuckDB diversifie le signal. |
| 2026-08-25 | Deux tables de faits (existant + neuf) partageant les mêmes dimensions | Une seule table plate mélangeant les deux régimes ; existant seulement | Pari initial (brief v1 = existant seulement). Confirmé le 2026-08-29 : le brief révisé impose les deux faits. Les dimensions partagées rendent les jointures légitimes sans fusionner les protocoles. |
| 2026-08-25 | Python pour l'ETL uniquement ; analyse 100 % SQL | Pandas pour les agrégations métier ; notebook unique | Le brief est un démonstrateur SQL. Pandas resterait un raccourci qui dilue le signal visé par le portfolio. Nuance 2026-08-29 : matplotlib + notebook de synthèse autorisés, uniquement pour illustrer des résultats SQL déjà calculés. |
| 2026-08-25 | Pas de cartographie / SIG | Folium, GeoPandas, PostGIS | Contrainte explicite du brief : agrégations géographiques via clés et `GROUP BY` seulement. Stretch 2026-08-29 : extension spatiale DuckDB (après les requêtes, si le temps le permet). |
| 2026-08-25 | Niveau portfolio : intermédiaire | Débutant | Fenêtres et CTE au-delà du SELECT/JOIN/GROUP BY ; schéma étoile à deux faits ; réconcilier deux régimes de mesure demande un jugement analytique, pas seulement de la syntaxe. |
| 2026-08-29 | Pont neuf vs existant = Espec (kWh/m².an), pas Ew | Fusionner les labels comme s'ils étaient un seul indicateur ; inventer un Ew manquant | L'open data publie Espec + label des deux côtés ; **Ew est absent**. Les seuils empiriques du label coïncident. Les protocoles restent distincts : on compare l'Espec en le disant, on ne compare pas la part de G (le neuf n'en a aucun). Détail : `docs/exploration.md`. |
| 2026-08-29 | Clé géographique = `mun_code` (code INS) | Joindre sur le nom de commune | 261 codes des deux côtés (l'API en dénombrait 258) ; les libellés `communes` / `commune` coïncident dans l'extrait, mais ne sont pas une clé. |
| 2026-08-29 | Grain des faits = certificat | Un bâtiment = une ligne | Des IDs *peuvent* se répéter (re-certifications). L'extrait Parquet chargé est déjà unique ; le schéma et l'ETL gardent le grain certificat. |
| 2026-08-29 | PK technique sur les faits ; chauffage en attribut dégénéré ; vue `v_certificats` comme pont Espec | PK = `id01_building` / `pebunit_id` ; dim chauffage partagée | Les IDs sources ne sont pas uniques *en général* (re-certifications). Chaudière existant (`device`) ≠ générateur neuf : vocabulaires incompatibles. La vue UNION ALL documente le pont sans fusionner les protocoles. |
| 2026-08-29 | Extraire tous les certificats (pas de dédup à l'ETL) | Ne garder que le plus récent par bâtiment | Le grain du schéma est le certificat. L'extrait Parquet du 2026-08-29 a déjà des IDs uniques (l'API Explore avait suggéré ~31 k re-certifs — écart d'agrégat, pas un filtre). Le « plus récent » se fera en fenêtre SQL à l'étape requêtes si besoin. |
| 2026-08-29 | Espec hors [-200, 1500] → NULL ; ligne conservée | Supprimer la ligne ; winsoriser | Un ++A négatif (ex. −15) est légitime (production > conso). −62 738 et les G > 1 500 faussent les médianes. On garde le certificat (label, commune) pour les volumes. |
| 2026-08-29 | Garder `scripts/` + `sql/load.sql` + `data/raw` / `data/processed` | Arborescence du brief (`src/import_clean.py`, `data/peb_wallonie.duckdb`) | Le brief décrit un gabarit. Trois scripts distincts (download, profil, ETL) et un `load.sql` versionné sont plus lisibles qu'un unique `import_clean.py`. Les extraits bruts restent gitignorés ; le `.duckdb` est régénérable. |
| 2026-08-29 | matplotlib + notebook **après** les requêtes SQL, pas avant | Dashboard (Streamlit/Dash) ; graphiques dès l'ETL | Le brief exige 2–3 figures statiques générées depuis le SQL, pas une couche BI. Le notebook `synthese_resultats.ipynb` n'apparaît qu'à l'étape synthèse. |
| 2026-08-29 | Extension spatiale DuckDB reportée (stretch) | L'activer maintenant, à la place du `GROUP BY` sur `mun_code` | Le cœur du brief reste « sans outil de cartographie ». Le code INS suffit pour commune / province. La jointure sur limites communales n'apporte un signal portfolio qu'une fois les 8–10 requêtes en place. |
| 2026-08-29 | Score de priorité = 60 % volume (m² F/G) + 40 % taux | Moyenne simple ; rang de médiane Espec ; volume seul | La synthèse oppose déjà Q02 (taux) et Q10 (m²) : le budget suit le volume, l'équité le taux. `percent_rank` reste lisible (0–100) et ne dépend pas d'unités. |
| 2026-08-29 | Spatial = polygones SPW + `ST_Touches` / `ST_Area`, pas de carte | Inventer des centroïdes de bâtiments ; Folium / GeoPandas | L'open data PEB résidentiel n'a pas de XY (anonymisé à la commune). Un point-in-polygon serait un faux. Les limites officielles (ADMUKEY = `mun_code`, Lambert 2008) permettent densité et voisinage, ce que le code INS ne encode pas. |
| 2026-08-29 | Classer les communes sur la **médiane** d'Espec, pas la moyenne | `AVG(espec)` comme dans l'exemple du brief | Même après clipping ETL, la moyenne reste tirée par les G hauts. La médiane est le thermomètre du « logement typique ». |
